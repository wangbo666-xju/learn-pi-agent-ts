# 第二阶段：模型语义流与 Context 管线

## 1. 这一阶段解决什么问题

第一阶段建立了 `AgentState` 与 `AgentEvent`，但真正的流式入口仍然长这样：

```ts
// src/real-llm.ts 现状（chatStream 内部）
onText(delta.content);          // ← 把“一段文本增量”直接丢给回调
```

以及编排端：

```ts
// src/agent.ts 现状
const reply = await this.llm.chatStream(
    messages,
    this.tools,
    (text) => process.stdout.write(text),   // ← Agent 直接打印终端
);
```

问题有三：

1. **回调语义太原始。** `onText(text)` 只知道“来了段文本”，分辨不出“流开始 / 文本增量 / 工具调用增量 / 结束”。以后 thinking、usage、取消都无从表达。
2. **模型适配器偷偷做 UI。** `RealLlmClient` 内部直接 `process.stdout.write()`，违背“适配器不负责终端”的边界。
3. **Context 没有统一的准备管线。** 以后要支持 Compact、上下文裁剪、外部注入，却不知道在哪一步插进去。

本阶段做两件事：

```text
LlmStreamEvent：模型流式语义事件（start / text_delta / toolcall_delta / done）
Context 管线：  transformContext(...) → convertToLlm(...) → LlmClient.chatStream(...)
```

它们不改变当前运行效果——模型还是那些模型、工具还是那些工具，只是把“流怎么进来、Context 怎么准备”这两个环节从 Agent 的 while 循环里拆出来，变成一个可注入、可测试的语义接口。

> 本阶段只是让 `RealLlmClient` / `FakeLlmClient` 用语义事件说话，并保留 `agent.ts` 现有行为（文本照常逐字上屏）。真正把 Context 管线接进 Agent Loop 是 Task 3 的事。

## 4. 第二步：定义并实现 Context 管线

创建 `src/context.ts`：

```ts
import type {
    AgentMessage,
    AssistantMessage,
    ToolResultMessage,
    UserMessage,
} from "./types.ts";

/**
 * 真正可以发给模型的角色集合。
 *
 * Agent 消息里可能还有“仅应用层可见”的角色（未来 Compact 摘要、备注等），
 * 但能发出去的只有 user / assistant / toolResult 三种。
 */
export type LlmMessage =
    | UserMessage
    | AssistantMessage
    | ToolResultMessage;

/** 发送前对完整上下文做最后一次加工（裁剪、Compact、外部注入）。 */
export type TransformContext = (
    messages: AgentMessage[],
    signal?: AbortSignal,
) => Promise<AgentMessage[]>;

/** 把 Agent 消息过滤成模型认识的 LlmMessage。 */
export type ConvertToLlm = (messages: AgentMessage[]) => LlmMessage[];

/** 默认：原样返回，不做任何裁剪。 */
export const identityTransformContext: TransformContext =
    async (messages) => messages;

/** 默认：只保留三种模型认识的角色（当前 AgentMessage 恰好只有这三种）。 */
export const defaultConvertToLlm: ConvertToLlm =
    (messages) => messages;

/**
 * 准备本轮模型请求的上下文：
 *   1. transformContext：可能增删改消息（后续承载 Compact / 注入）；
 *   2. convertToLlm：过滤出模型认识的 LlmMessage。
 */
export async function prepareLlmContext(
    messages: AgentMessage[],
    transformContext: TransformContext = identityTransformContext,
    convertToLlm: ConvertToLlm = defaultConvertToLlm,
    signal?: AbortSignal,
): Promise<LlmMessage[]> {
    const transformed = await transformContext([...messages], signal);
    return convertToLlm(transformed);
}
```

### 为什么先 transform 再 convert

- `transformContext` 工作在**完整 Agent 上下文**上，它可能需要参考被裁剪掉的部分来决定保留哪些（例如 Compact 摘要依赖全部历史），所以它先跑、拿到全量。
- `convertToLlm` 是纯函数过滤，只关心“留下哪三种角色”，放在最后跑，保证输出就是能直接序列化给模型的 `LlmMessage[]`。

当前 `AgentMessage` 恰好只含 `user / assistant / toolResult`，所以 `defaultConvertToLlm` 看起来像恒等函数。它真正的价值是**锁定边界**：以后在 `AgentMessage` 里加新角色时，这里就是唯一需要记得过滤的地方。

## 5. 第三步：定义 LlmStreamEvent 并改 chatStream 协议

### 5.1 `src/types.ts` 里新增语义事件

```ts
/** 模型流式生成 assistant 消息时的语义事件。 */
export type LlmStreamEvent =
    | {
        type: "start";
        /** 最初的空 partial 快照。 */
        partial: AssistantMessage;
    }
    | {
        type: "text_delta";
        delta: string;
        /** 累积到当前的全部文本。 */
        partial: AssistantMessage;
    }
    | {
        type: "toolcall_delta";
        /** 累积到当前的内容；工具参数碎片尚未成段，暂不放进快照。 */
        partial: AssistantMessage;
    }
    | {
        type: "done";
        /** 组装完成、含最终 toolCalls 的完整消息。 */
        message: AssistantMessage;
    };
```

> **关于 `toolcall_delta` 的快照**：流式工具调用时，`arguments` 是逐片到达的 JSON 碎片（例如先 `{"pat` 后 `h":"a"}`），在流结束前**不是合法 JSON**，无法解析成 `ToolArguments`。因此 `toolcall_delta` 阶段只把累积到的文本放进 `partial`，真正的 `toolCalls`（含解析后的参数）延迟到 `done` 事件才给出。这是本学习版采取的策略——先保证不因碎片解析抛错。

### 5.2 改 `chatStream` 签名

把第三参从 `onText` 换成 `onEvent`：

```ts
export interface LlmClient {
    chat(
        messages: AgentMessage[],
        tools: Tool[],
        options?: LlmRequestOptions,
    ): Promise<AssistantMessage>;

    chatStream(
        messages: AgentMessage[],
        tools: Tool[],

```

**连带修改**：`agent.ts` 是唯一调用 `chatStream` 的地方（grep 可确认），签名一变它立刻编译不过，必须同步适配，见 §8。

## 6. 第四步：重写 RealLlmClient.chatStream 为语义事件

现在的 `chatStream`（`src/real-llm.ts`）在 `readSseChunks` 里直接 `onText(delta.content)`，流结束后才组装 `toolCalls`。改成：流内维护一个累计的 `partial`，每次内容增量发 `text_delta`，有工具碎片发 `toolcall_delta`，流结束后组装完整消息并发 `done`。

```ts
async chatStream(
    messages: AgentMessage[],
    tools: Tool[],
    onEvent: (event: LlmStreamEvent) => void | Promise<void>,
    options?: LlmRequestOptions,
): Promise<AssistantMessage> {
    const {apiKey, baseUrl, model} = requireConfig();

    const response = await fetch(`${baseUrl}/chat/completions`, {
        method: "POST",
        headers: {
            Authorization: `Bearer ${apiKey}`,
            "Content-Type": "application/json",
        },
        body: JSON.stringify({
            model,
            stream: true,
            messages: toApiMessages(messages, options?.systemPrompt),
            tools: toApiTools(tools),
            tool_choice: "auto",
        }),
    });
    if (!response.ok) {
        throw new Error(`模型请求失败：${response.status} ${await response.text()}`);
    }

    let content = "";
    // 按 index 分组累加工具调用碎片（与之前一致）。
    const toolCallFragments = new Map<number, {
        id: string;
        name: string;
        argumentsText: string;
    }>();

    // start：流正式开始，先给一个空 partial。
    await onEvent({
        type: "start",
        partial: {role: "assistant", content: ""},
    });

    await readSseChunks(response, async (chunk) => {
        const delta = chunk.choices[0]?.delta;
        if (!delta) {
            return;
        }

        if (delta.content) {
            content += delta.content;
            // 只发语义增量，绝不在此处 process.stdout.write。
            await onEvent({
                type: "text_delta",
                delta: delta.content,
                partial: {role: "assistant", content},
            });
        }

        let hasToolFragment = false;
        for (const fragment of delta.tool_calls ?? []) {
            const index = fragment.index ?? 0;
            let acc = toolCallFragments.get(index);
            if (!acc) {
                acc = {
                    id: fragment.id ?? "",
                    name: fragment.function?.name ?? "",
                    argumentsText: "",
                };
                toolCallFragments.set(index, acc);
            }
            if (fragment.id) acc.id = fragment.id;
            if (fragment.function?.name) acc.name = fragment.function.name;
            if (fragment.function?.arguments) acc.argumentsText += fragment.function.arguments;
            hasToolFragment = true;
        }
        if (hasToolFragment) {
            // 工具参数是 JSON 碎片，尚未成段，partial 只反映已累积文本。
            await onEvent({
                type: "toolcall_delta",
                partial: {role: "assistant", content},
            });
        }
    });

    // 流结束：按 index 组装，与非流式 chat() 结构一致。
    const toolCalls = [...toolCallFragments.entries()]
        .sort((a, b) => a[0] - b[0])
        .map(([, {id, name, argumentsText}]) => ({
            id,
            name,
            arguments: argumentsText ? parseToolArguments(argumentsText) : {},
        }));

    const message: AssistantMessage = {
        role: "assistant",
        content,
        toolCalls: toolCalls.length ? toolCalls : undefined,
    };

    // done：给出完整消息（此时 toolCalls 才真正可解析）。
    await onEvent({type: "done", message});

    return message;
}
```

注意两点：

- **`RealLlmClient` 里不再出现 `process.stdout.write()`。** 流内 `onText` 删除，`onEvent` 只传递语义。
- `readSseChunks` 的 `onChunk` 回调现在是 async（因为我们 `await onEvent`），其 `while` 循环里调用处需要加上 `await`：

```ts
await readSseChunks(response, async (chunk) => { ... });
```

`readSseChunks` 本身的类型保持 `onChunk: (chunk: StreamChunk) => void | Promise<void>`，并在循环里 `await onChunk(...)`，这样 async 回调才会真正被等待。

> `streamText` 方法不在 `LlmClient` 协议上，也不是 Agent 主路径的依赖，本阶段可先不动；如需彻底对齐“适配器不写终端”，可另开提交清理。

## 7. 第五步：同步 FakeLlmClient

`src/fake-llm.ts` 的 `chatStream` 也要发同样语义事件，否则测试夹具与真实模型行为不一致：

```ts
async chatStream(
    messages: AgentMessage[],
    tools: Tool[],
    onEvent: (event: LlmStreamEvent) => void | Promise<void>,

    const response = await this.chat(messages, tools);
```

## 8. 第六步：适配 agent.ts 唯一调用点

`agent.ts` 现在把第三参当文本回调。改成事件处理器，只有 `text_delta` 才写终端，行为保持不变：

```ts
const reply = await this.llm.chatStream(
    messages,
    this.tools,
    (event) => {
        // 只在文本增量时上屏；工具调用阶段不打印。

        systemPrompt: this.systemPrompt,
```

此时 `agent.ts` 里那行 `process.stdout.write("\n")`（给两轮文本补换行）仍可保留，不影响本阶段验收。真正把打印逻辑移到 CLI、让 Agent 不再写终端，属于 Task 3 的范围。

## 9. 第七步：增加 SSE 语义事件顺序测试

`src/real-llm.ts` 的 `chatStream` 现在从“回调攒文本”变成“发 start / delta / done 语义事件”，值得在 `test/real-llm.test.ts` 里用 fetch mock + `ReadableStream` 锁住顺序。新增一个测试：

```ts
import assert from "node:assert/strict";
import test from "node:test";
import {RealLlmClient} from "../src/real-llm.ts";
import type {LlmStreamEvent} from "../src/types.ts";

test("chatStream 按 start → text_delta → done 顺序发出语义事件", async () => {
    const originalFetch = globalThis.fetch;
    const originalApiKey = process.env.OPENAI_API_KEY;
    const originalBaseUrl = process.env.OPENAI_BASE_URL;
    const originalModel = process.env.OPENAI_MODEL;

    process.env.OPENAI_API_KEY = "test-key";
    process.env.OPENAI_BASE_URL = "https://example.test";
    process.env.OPENAI_MODEL = "test-model";

    // 用两个 data: 帧 + [DONE] 构造 SSE 流。
    const encoder = new TextEncoder();
    const sseBody = new ReadableStream<Uint8Array>({
        start(controller) {
            controller.enqueue(encoder.encode(
                'data: {"choices":[{"delta":{"role":"assistant","content":"Hel"}}]}\n\n',
            ));
            controller.enqueue(encoder.encode(
                'data: {"choices":[{"delta":{"role":"assistant","content":"lo"}}]}\n\n',
            ));
            controller.enqueue(encoder.encode("data: [DONE]\n\n"));
            controller.close();
        },
    });

    globalThis.fetch = async () =>
        new Response(sseBody, {status: 200});

    const received: string[] = [];
    let finalContent = "";

    try {
        const client = new RealLlmClient();
        const result = await client.chatStream(
            [{role: "user", content: "hi"}],
            [],
            (event) => {
                received.push(event.type);
                if (event.type === "text_delta") {
                    finalContent += event.delta;
                }
            },
        );

        assert.deepEqual(received, ["start", "text_delta", "text_delta", "done"]);
        assert.equal(finalContent, "Hello");
        assert.equal(result.content, "Hello");
    } finally {
        globalThis.fetch = originalFetch;
        process.env.OPENAI_API_KEY = originalApiKey;
        process.env.OPENAI_BASE_URL = originalBaseUrl;
        process.env.OPENAI_MODEL = originalModel;
    }
});
```

把 `received` 展开写出的原因：它一次把“语义事件顺序”和“最终文本”都锁住了。`start` 是 `chatStream` 在读流之前就发出的，因此一定排在两个 `text_delta` 之前。

## 11. 建议断点位置

### `RealLlmClient.chatStream` 里 `await onEvent(...)`

观察一次文本流：

```text
start (content: "")
text_delta ("Hel", partial.content: "Hel")
text_delta ("lo", partial.content: "Hello")
done  (message.content: "Hello")
```

确认每次 `partial` 都是**完整快照**，而不是增量——这正是 Task 3 里编排器能“无状态原地替换”的基础。

### 工具调用场景

断点停在 `toolcall_delta` 分支与最后的 `done`：

```text
toolcall_delta: partial.content 不变，toolCalls 尚未出现
done:           message.toolCalls 已含解析后的 arguments
```

### `prepareLlmContext`

传入自定义 `transformContext`（往数组 push 一条注入消息），断点看：

```text
入参 messages 长度 = 原始长度
transformContext 返回后 = 原始长度 + 1
convertToLlm 收到的是 transform 后的结果
调用方原始 messages 数组未被改动（副本）
```

## 12. 本阶段完成后的效果

对外运行效果**暂时不变**——文本照常流式上屏，工具照常执行。变化都在“内部协议层”：

```text
之前：chatStream(messages, tools, onText)   // 一段文本裸回调
现在：chatStream(messages, tools, onEvent)  // start / text_delta / toolcall_delta / done

之前：Context 怎么准备散落在 Agent 循环里
现在：prepareLlmContext(messages, transform, convert, signal) 一条管线
```

这两样是 Task 3（抽取 `agent-loop`、把 Agent 改成订阅 `AgentEvent` 编排）的挂靠点：Agent Loop 将用 `prepareLlmContext` 准备上下文，再把 `LlmStreamEvent` 翻译成第一阶段定义的 `message_start / message_update / message_end`，从而摆脱 `process.stdout.write`。
